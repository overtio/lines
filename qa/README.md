# QA

What to check before a release, and the notes to check it with.

- **[checklist.md](checklist.md)**: every interaction in lines, as a list of todos. It's also a note: adding the QA notes to lines adds it, so a tester can tick it off in the app.
- **[notes/](notes/)**: notes that show everything a note can hold, on its own and combined. Generated by `scripts/qa-notes.mjs`; don't edit them by hand.
- **shots/** (not kept in git): pictures of lines to look over, each look and feature in light and dark, at a desktop's width and a phone's, with what to look for beside each. `bun run qa-shots` takes them (`--browser webkit` for WebKit's, `--only paper,typing` for some), and `qa/shots/index.html` shows them.

What can be checked by a program is, by the tests in `tests/` (`bun run test`, `bun run test:browser`): these are for what needs a person's eye.
  - `01`–`08`: inline styles, tags and highlights, callouts, edge cases, constructs left unclosed, and links drawn short (GitHub, arXiv).
  - `09-latex.tex`: a note written in LaTeX ([docs/latex.md](../docs/latex.md)), with everything lines draws in one.
  - `10`–`16`: every element inside every container (top level, card, callout, callout with no icon, callout in a card, quote, list item).
  - `17`–`19`: objects: two notes with properties and a type (a person and a company), mentions of them, and tables of a type.
  - `20`–`62`: every element followed straight away by every other, with no blank line between.

## Before a release

1. Take the pictures (`bun run qa-shots`, and `--browser webkit`) and look through `qa/shots/index.html`: each says what to look for.
2. On each platform you ship (Mac app, web in Chrome and Safari, phone width), start from a fresh profile.
3. Settings → Export and Import → **Add QA Notes**. The notes are added alongside any others, tagged `qa`.
4. Open **QA · Release checklist** and work through it, ticking items off. Each QA note says at the top what to check in it. Look at them in light and dark, and at phone width.
5. File anything that's wrong, with the note and section number (e.g. "11-card #14").

The demo website works too: open it in a private window and add the QA notes there.

## When a feature changes

Every change that users can see updates these in the same change:

- **Something new a note can hold, or a new way of writing one:** add it to `ELEMENTS` (and to `CONTAINERS` if things go inside it) in `scripts/qa-notes.mjs`, run `bun run qa-notes`, and commit the notes it writes. Also update [docs/linedown.md](../docs/linedown.md). For LaTeX notes, it's `LATEX` in the same script, and [docs/latex.md](../docs/latex.md).
- **A new interaction** (a shortcut, a button, a menu item, a gesture, a setting, a behaviour): add a line to [checklist.md](checklist.md) under its area, saying what to do and what should happen, with the platform in brackets if it's limited to one.
- **A new feature worth showing:** add it to the feature tour (`src/lib/notes/tour/`), which the demo website starts with.
- **Something that looks a new way** (a look, a setting that changes how something's drawn, a block a note can have): add a scene to `SCENES` in `scripts/qa-shots.mjs`, saying what to look for, and its tests to `tests/`.
